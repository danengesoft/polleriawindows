# Guía del módulo clínica (examen final práctico v7)

Esta guía explica, paso a paso y archivo por archivo, cómo se construyó el módulo `clinica`
dentro del proyecto de la pollería. Está ordenada **en el mismo orden en que conviene hacerlo
en un examen**: base de datos → backend → SPA, primero la pregunta 1 y después la 2.

Cada sección dice **qué ítem del examen cubre**, **en qué sesión del curso se vio** y **qué
archivo del proyecto de la pollería sirve de modelo**, para que puedas repetirlo tú solo.

## 1. Base de datos (pregunta 1 · 2 pts)

**Sesión:** S01 (esquema por módulo). **Archivo:** `polleria-backend/scripts/02-clinica.sql`.

Es el **Anexo B** del examen (scripts 1 y 2 para PostgreSQL), sin cambios:

- `CREATE SCHEMA EXA_CLINICA;`: en PostgreSQL el **esquema** cumple el papel del **usuario** de
  Oracle. Agrupa las tablas del módulo.
- 4 tablas:
  - `CLINICAS`: tiene `RUC` único.
  - `CONSULTORIOS`: tiene una FK a `CLINICAS`, `CODIGO` único, `TARIFA_HORA > 0` y un `CHECK`
    sobre el estado.
  - `ESPECIALIDADES`.
  - `CONSULTORIO_ESPECIALIDAD`: la **tabla intermedia** de la relación muchos a muchos. Su PK es
    compuesta (`ID_CONSULTORIO`, `ID_ESPECIALIDAD`) y cada una de esas dos columnas es FK.
- Al final vienen las semillas: 3 clínicas, 4 consultorios, 5 especialidades y 3 asignaciones.

`iniciar.bat` lo ejecuta solo la primera vez, mediante `windows/postgres/crear-tablas.sh`. En el
examen lo ejecutarías tú con PowerShell. Para **listar las tablas** (script 3 del examen):

```powershell
$DB = 'polleria-prodtest-postgres-1'
@'
SELECT table_name FROM information_schema.tables WHERE table_schema = 'exa_clinica' ORDER BY 1;
'@ | docker exec -i $DB psql -U polleria -d polleria
```

> PostgreSQL convierte a minúsculas los nombres que no van entre comillas: `EXA_CLINICA.CLINICAS`
> queda como `exa_clinica.clinicas`. Por eso en `information_schema` se busca `'exa_clinica'`.

## 3. CRUD de clínicas (pregunta 1 · 4 pts + 1 pt de validaciones)

**Sesiones:** S02 (CRUD REST completo) y S07/S08 (SPA). **Modelo en la pollería:** `catalogo/categoria`.

### 3.1 Entidad `Clinica.java`

```java
@Entity
@Table(name = "CLINICAS", schema = "EXA_CLINICA")
public class Clinica {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @Column(name = "ID")
    private Long id;

    @JdbcTypeCode(SqlTypes.CHAR)                       // la columna es CHAR(11)
    @Column(name = "RUC", nullable = false, length = 11, unique = true)
    private String ruc;
    ...
    @Convert(converter = NumericBooleanConverter.class) // 0/1 en la base ↔ true/false en Java
    @JdbcTypeCode(SqlTypes.SMALLINT)                    // la columna es SMALLINT
    @Column(name = "ACTIVO", nullable = false)
    private Boolean activo = true;
}
```

- `schema = "EXA_CLINICA"`: indica en qué esquema está la tabla.
- `GenerationType.IDENTITY`: el `ID` lo genera la base de datos (`GENERATED BY DEFAULT AS IDENTITY`).
- **Por qué `@JdbcTypeCode`:** el proyecto arranca con `ddl-auto: validate`, es decir, Hibernate
  compara cada entidad con la tabla real y, si un tipo no coincide, **el backend no arranca**.
  `CHAR(11)` y `SMALLINT` no son los tipos que Hibernate espera por defecto para `String` y
  `Boolean`, así que se le indican explícitamente.

### 3.2 DTO con las validaciones del examen: `ClinicaRequest.java`

```java
@NotBlank(message = "El RUC es obligatorio")
@Pattern(regexp = "\\d{11}", message = "El RUC debe tener 11 dígitos")
private String ruc;

@NotBlank(message = "La razón social es obligatoria")
private String razonSocial;
```

El controlador recibe `@Valid @RequestBody ClinicaRequest`. Si algo no cumple, Spring responde
**400** antes de llegar al servicio. El examen pide además que el error **se vea en el formulario**,
y eso lo hace la SPA (sección 3.6).

Se separan `Request` (lo que entra) y `Response` (lo que sale) para no exponer la entidad JPA,
como en S02.

### 3.3 Mapper (MapStruct): `ClinicaMapper.java`

```java
@Mapper(componentModel = "spring", unmappedTargetPolicy = ReportingPolicy.ERROR)
public interface ClinicaMapper {
    @Mapping(target = "id", ignore = true) Clinica toEntity(ClinicaRequest request);
    ClinicaResponse toResponse(Clinica clinica);
    @Mapping(target = "id", ignore = true) void actualizar(ClinicaRequest r, @MappingTarget Clinica c);
}
```

MapStruct genera la implementación al compilar. `unmappedTargetPolicy = ERROR` hace que el build
falle si olvidas un campo, igual que en `CategoriaMapper`.

### 3.4 Repositorio: `ClinicaRepository.java`

```java
boolean existsByRuc(String ruc);
boolean existsByRucAndIdNot(String ruc, Long id);   // al editar, excluye la clínica que editas
```

Spring Data crea la consulta a partir del **nombre del método**.

### 3.5 Servicio y controlador

`ClinicaServiceImpl`:

| Método | Qué hace |
|---|---|
| `crear` | Rechaza un RUC repetido con **409** (`BusinessConflictException`) |
| `actualizar` | Igual que `crear`, pero excluye la clínica que se está editando |
| `eliminar` | Si la clínica tiene consultorios, responde **409** con un mensaje claro en lugar de dejar que falle la FK |
| `buscarOFallar` | Responde **404** (`ResourceNotFoundException`) si el id no existe |

`ClinicaController` expone los 5 endpoints REST:

| Método | URL | Respuesta |
|---|---|---|
| GET | `/api/v1/clinica/clinicas` | 200 + lista |
| GET | `/api/v1/clinica/clinicas/{id}` | 200 / 404 |
| POST | `/api/v1/clinica/clinicas` | 201 + `Location` / 400 / 409 |
| PUT | `/api/v1/clinica/clinicas/{id}` | 200 / 400 / 404 / 409 |
| DELETE | `/api/v1/clinica/clinicas/{id}` | 204 / 404 / 409 |

Las excepciones las convierte en JSON el `GlobalExceptionHandler` que ya existía (S02).

### 3.6 SPA: servicio, listado y formulario

- **`clinica.model.ts`:** interfaces TypeScript iguales a los DTO (`Clinica`, `ClinicaRequest`…).
- **`clinica-service.ts`:** un método por endpoint, con `HttpClient`. El token JWT lo agrega el
  interceptor que ya existía (S11): el servicio no se encarga de la seguridad.
- **`clinica-list` (Figura 2):**
  - Carga los datos en una `signal`, `datos = signal<Clinica[]>([])`, y los muestra con
    `@for (item of datos(); track item.id)`.
  - **Eliminar** abre el diálogo `ConfirmarEliminacion` y, si confirmas, llama al servicio y
    recarga la lista.
- **`clinica-form` (Figura 3):** una sola pantalla para crear (`/nuevo`) y editar (`/:id/editar`).
  1. Si la ruta trae `id`, carga la clínica y llena el formulario con `patchValue`.
  2. El formulario reactivo tiene las mismas reglas que el backend:
     ```ts
     ruc: ['', [Validators.required, Validators.pattern(/^\d{11}$/)]],
     razonSocial: ['', [textoObligatorio, Validators.maxLength(150)]],
     ```
  3. Al pulsar **Guardar** con errores se ejecuta `markAllAsTouched()`. Eso marca todos los
     campos como tocados y hace que `<mat-error>` muestre cada mensaje
     (*"× El RUC debe tener 11 dígitos"*, *"× La razón social es obligatoria"*). **Esto es lo
     que el docente pide ver.**
  4. Si todo está bien, llama a `crearClinica` o `actualizarClinica` y vuelve al listado con un
     aviso.

## 5. Consultorio con sus especialidades: cabecera con detalles (pregunta 2 · 12 pts)

**Sesiones:** S03 (relación con lista desplegable), S04 (cabecera con detalles en el backend) y
S09 (formulario transaccional en la SPA). **Modelo en la pollería:** `pedidos/pedido`
(`PedidoServiceImpl.crear` y `pedido-form`).

Es la misma idea que **Venta con sus DetalleVenta**: el consultorio es la **cabecera** y las
especialidades son sus **líneas**. La diferencia es que aquí cada línea no es una fila con
cantidad y precio, sino solo una **referencia** a una especialidad que ya existe. Por eso la tabla
de detalle es la tabla intermedia `CONSULTORIO_ESPECIALIDAD`.

### 5.1 Entidad `Consultorio.java`

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "ID_CLINICA", nullable = false)
private Clinica clinica;                              // la clínica elegida en la lista desplegable (S03)

@Enumerated(EnumType.STRING)
@Column(name = "ESTADO", nullable = false, length = 20)
private EstadoConsultorio estado;                     // DISPONIBLE, OCUPADO o MANTENIMIENTO

@ManyToMany
@OrderBy("codigo ASC")
@JoinTable(name = "CONSULTORIO_ESPECIALIDAD", schema = "EXA_CLINICA",
        joinColumns = @JoinColumn(name = "ID_CONSULTORIO"),
        inverseJoinColumns = @JoinColumn(name = "ID_ESPECIALIDAD"))
private Set<Especialidad> especialidades = new LinkedHashSet<>();   // las líneas
```

- `@ManyToOne`: muchos consultorios pertenecen a una clínica (columna FK `ID_CLINICA`).
- `@Enumerated(EnumType.STRING)`: guarda el **nombre** del enumerado (`'OCUPADO'`), que es lo
  que exige el `CHECK` de la tabla. Con `ORDINAL` guardaría 0, 1, 2 y el `CHECK` fallaría.
- `@ManyToMany` con `@JoinTable`: describe la tabla intermedia. `Consultorio` es el **dueño** de
  la relación, así que:
  - al guardar un consultorio, Hibernate inserta sus filas en `CONSULTORIO_ESPECIALIDAD`;
  - al eliminarlo, **primero borra esas filas** y después la cabecera, así que la FK no falla.
- Se usa un `Set` porque una especialidad no puede repetirse en el mismo consultorio (la PK
  compuesta tampoco lo permitiría).

### 5.2 DTO compuesto: `ConsultorioRequest.java`

```java
@NotNull private Long clinicaId;                     // cabecera
@NotBlank @Size(max = 10) private String codigo;
@NotNull @DecimalMin(value = "0", inclusive = false) private BigDecimal tarifaHora;
@NotNull private EstadoConsultorio estado;           // Spring rechaza (400) un valor que no esté en el enum
@NotEmpty private List<@NotNull @Positive Long> especialidadIds;    // líneas
```

La SPA envía **todo en una sola petición**, como `VentaRequest` con su lista de detalles en S04:

```json
{ "clinicaId": 1, "codigo": "CON-301", "tarifaHora": 95.50, "estado": "DISPONIBLE",
  "especialidadIds": [1, 3] }
```

`ConsultorioResponse` devuelve la cabecera, más `clinicaRazonSocial` para mostrarla en el
listado, más la lista `especialidades` (código y nombre).

### 5.3 Repositorio con `@EntityGraph`

```java
@Override
@EntityGraph(attributePaths = {"clinica", "especialidades"})
List<Consultorio> findAll(Sort sort);
```

Sin `@EntityGraph`, listar 10 consultorios haría 1 consulta para los consultorios más 20 más
(una por la clínica y otra por las especialidades de cada uno): es el **problema N+1** de S03/S04.
Con `@EntityGraph`, Hibernate lo resuelve todo con un `JOIN`.

### 5.4 Servicio: registro atómico (`ConsultorioServiceImpl.crear`)

```java
@Transactional
public ConsultorioResponse crear(ConsultorioRequest request) {
    // 1. código único → si se repite, 409
    // 2. la clínica debe existir → si no, 404
    // 3. las especialidades deben existir todas → si falta alguna, 400
    Set<Long> ids = new LinkedHashSet<>(request.getEspecialidadIds());   // quita repetidos
    List<Especialidad> especialidades = especialidadRepository.findAllById(ids);
    if (especialidades.size() != ids.size()) throw new InvalidRequestException(...);
    // 4. arma la cabecera, le agrega sus líneas y guarda TODO junto
    consultorio.getEspecialidades().addAll(especialidades);
    return mapper.toResponse(consultorioRepository.save(consultorio));
}
```

`@Transactional` hace que la operación sea **atómica** (S04): o se guardan la cabecera y todas sus
líneas, o no se guarda nada. Se comprobó enviando una especialidad inexistente: responde 400 y no
queda ningún consultorio a medias en la base.

`eliminar` busca el consultorio y llama a `delete`. Hibernate se encarga de borrar primero las
líneas.

### 5.5 SPA: nuevo consultorio con sus líneas (`consultorio-form`, Figura 5)

- **Cabecera:** un formulario reactivo con:
  - `mat-select` de **clínicas**, cargado con `listarClinicas()` y filtrado a las activas;
  - código y tarifa;
  - `mat-select` de **estado**, con las opciones de `ESTADOS_CONSULTORIO`.
- **Líneas:** una `signal` aparte:
  ```ts
  readonly asignadas = signal<Especialidad[]>([]);
  agregar()  { this.asignadas.update(l => [...l, especialidad]); }   // botón Agregar
  quitar(e)  { this.asignadas.update(l => l.filter(x => x.id !== e.id)); } // botón Quitar
  readonly disponibles = computed(() => /* especialidades que aún no se agregaron */);
  ```
  - `computed` saca de la lista desplegable las especialidades ya agregadas, así que no se puede
    repetir una.
  - La tabla de asignadas se dibuja con `@for (e of asignadas(); ...)`.
- **Guardar:**
  1. Valida la cabecera (`markAllAsTouched`) y que haya al menos una línea.
  2. Arma el `ConsultorioRequest` con `especialidadIds: this.asignadas().map(e => e.id)` y lo
     envía en **una sola petición** POST.

### 5.6 SPA: listado, detalle y eliminar (Figuras 4 y 6)

- **`consultorio-list`:**
  - Tabla con código, clínica, tarifa (`| number: '1.2-2'`) y estado.
  - **Ver** navega a `/interno/clinica/consultorios/:id`.
  - **Eliminar** pide confirmación, llama a `DELETE` y recarga la lista.
- **`consultorio-detalle`:** muestra en solo lectura la cabecera y la tabla de **especialidades
  asignadas**, que llegan en la misma respuesta de `GET /consultorios/{id}`.

## 6. Seguridad y navegación

**Sesiones:** S10b (backend con Keycloak) y S11 (frontend con Keycloak).

- **Backend:** `SecurityConfig.java` tiene una regla nueva:
  ```java
  .requestMatchers("/api/v1/clinica/**").hasRole("ADMINISTRADOR")
  ```
  Va **antes** de `.anyRequest().denyAll()`; si no, todo el módulo respondería 403. Comprobado:
  - sin token responde **401**;
  - con rol CAJERO responde **403**;
  - con ADMINISTRADOR responde **200**.
- **SPA:** las rutas `clinica/...` de `app.routes.ts` usan `canActivate: [rolGuard('ADMINISTRADOR')]`.
  El menú lateral (`interno.html`) tiene la sección **Clínica** con tres enlaces: Clínicas,
  Especialidades y Consultorios.

## 8. Cómo repetirlo tú solo en 120 minutos

| Minutos | Qué hacer | Copiar la forma de… |
|---:|---|---|
| 0–10 | Ejecutar los scripts 1, 2 y 3 del examen y listar las tablas | Sección 1 de esta guía |
| 10–35 | Backend de `Clinica`: entidad, DTO con `@Pattern`/`@NotBlank`, mapper, repositorio, servicio y controlador, más la regla en `SecurityConfig` | `catalogo/categoria` |
| 35–55 | SPA de clínicas: modelo, servicio, listado, formulario y rutas | `features/catalogo/categoria` |
| 55–65 | Especialidades: entidad, repositorio, GET y la tabla en la SPA | — |
| 65–90 | Backend de `Consultorio`: `@ManyToOne`, `@Enumerated`, `@ManyToMany` con `@JoinTable`, DTO con `especialidadIds`, servicio `@Transactional` | `pedidos/pedido` y S04 |
| 90–115 | SPA de consultorios: formulario con la `signal` de líneas (agregar y quitar), listado, detalle y eliminar | `features/pedidos/pedido-form` y S09 |
| 115–120 | Dejar todo en ejecución y probar la Tabla 3 | Sección 7 |

**Errores frecuentes que aparecieron al construirlo:**

1. **El backend no arranca: `wrong column type … found [int2], but expecting [integer]`.**
   La columna es `SMALLINT` y Hibernate esperaba `INTEGER`. Se soluciona con
   `@JdbcTypeCode(SqlTypes.SMALLINT)`; para `CHAR(11)`, con `@JdbcTypeCode(SqlTypes.CHAR)`.
2. **403 en todo el módulo:** falta el `requestMatchers` de `/api/v1/clinica/**` antes de
   `denyAll()`.
3. **El estado no se guarda (error de `CHECK`):** falta `@Enumerated(EnumType.STRING)`.
4. **No se puede eliminar un consultorio por la FK:** pasa si se usa un SQL a mano en lugar de
   `@ManyToMany`, porque hay que borrar primero las filas de `CONSULTORIO_ESPECIALIDAD`.
5. **Los errores no aparecen en el formulario:** falta `markAllAsTouched()` antes de salir de
   `guardar()`, o falta el `<mat-error>` dentro de `<mat-form-field>`.
